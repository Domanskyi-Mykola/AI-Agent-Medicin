# Архітектура Trauma AI (MVP)

Документ фіксує прийняті рішення і те, що свідомо спрощено або відкладено, щоб при масштабуванні не сплутати MVP-компроміси з фінальною архітектурою.

## Ключові рішення

### Відповідь чату: гібридний режим (`ANSWER_MODE=hybrid`, за замовчуванням з 2026-09)
**Чому змінено.** На демонстрації медконсультанту (2026-09) строгий режим «лише з бази знань» на більшість питань відповідав «недостатньо даних»: у базі було 2 файли, а лікар питав про весь спектр травматології. Для валідації це марно — консультант не може оцінити клінічну якість відповіді, якої немає.

**Як працює.** Claude повертає структурований JSON (structured outputs, схема `CHAT_SCHEMA` у `app/prompts.py`) з чотирма полями:
- `out_of_scope` — питання поза травматологією/ортопедією → детермінована відмова `OUT_OF_SCOPE_ANSWER`;
- `kb_answer` — **лише** з фрагментів бази знань, кожне твердження з посиланням `[N]`;
- `general_answer` — те, чого бракує в базі, із загальних знань моделі, **без посилань**; в UI — окремий жовтий блок «Загальні клінічні знання AI» з попередженням перевірити;
- `kb_coverage` — full/partial/none (показується в UI).

Межа між «з джерела» і «зі знань моделі» — видима для лікаря, а не прихована в тексті. `api/chat.py` додатково: цитати формуються лише для номерів, реально згаданих у `kb_answer` (regex `[N]`); якщо модель поставила kb-частину без жодного посилання — вона переноситься в `general_answer` (не видаємо непідтверджене за «з бази»).

**Строгий режим** (`ANSWER_MODE=strict`) зберігає початкову поведінку: `general_answer` завжди порожній, а якщо `retrieve()` повернув 0 чанків — Claude не викликається взагалі, відповідь «недостатньо даних». Повернути строгий режим — одна змінна в `.env`, без змін коду (варіант для зовнішнього показу, див. TODO «Звуження позиціонування»).

- Поріг релевантності: `RAG_MAX_DISTANCE` (косинусна відстань, 1 − cos_sim). Підбирається під embedding-модель.
- Системний промпт вимагає: посилання на джерело для кожного твердження kb-частини, заборону вигадувати дані пацієнта, обережні формулювання там, де немає консенсусу, дозування лише стандартні з приміткою «перевірте за протоколом», стислість (~150–350 слів).

**Калібрований поріг і його межа (виміряно на прикладних джерелах, multilingual-e5-base):**

| Тип запиту | top-3 дистанції |
|---|---|
| Релевантний (типи переломів AO/OTA) | 0.093 / 0.115 / 0.135 |
| Релевантний перефраз (відкритий перелом гомілки) | 0.152 / 0.190 / 0.192 |
| Нерелевантний медичний (кардіологія) | 0.187 / 0.201 / 0.217 |
| Нерелевантний медичний (гастро) | 0.190 / 0.203 / 0.206 |
| Нерелевантний немедичний (погода) | 0.239 / 0.261 / 0.268 |

Висновок: релевантні перефрази (до 0.192) і медично-суміжні чужі теми (кардіологія від 0.187) **перекриваються** — самим лише порогом їх чисто не розділити (обмеження малої мультимовної моделі на однодоменному тексті). Тому захист дворівневий: (1) поріг `0.22` відсікає грубо чуже (погода → детермінований «недостатньо даних», без виклику LLM); (2) медично-суміжні поза травматологією відсіює LLM за правилом 4 системного промпта. Справжнє рішення для тонкої тематичної фільтрації — краща/більша embedding-модель або реранкер (див. TODO).

### Цитування
Нумерація детермінована: чанки нумеруються `[1..N]` у промпті; кожен елемент `citations` у відповіді API має поле `n`, що дорівнює номеру `[n]` у тексті. У список потрапляють **лише** джерела, на які модель реально послалась у `kb_answer` (раніше показувались усі знайдені чанки, включно з нерелевантними). Метадані джерела беруться з чанків, а не з тексту моделі.

### Дисклеймер
Додається до кожної відповіді **детерміновано** (окреме поле API), не покладаючись на модель.

### Абстракція VectorStore
`app/rag/vector_store.py` визначає інтерфейс `VectorStore` (add/query/count/reset). Реалізація — `ChromaVectorStore`. Перехід на pgvector/Pinecone = нова реалізація інтерфейсу без змін у retriever/ingestion.

### Модель Claude у конфігу
Назва моделі винесена в `CLAUDE_MODEL` (`.env`). `claude-sonnet-5` не приймає `temperature`/`top_p`/`budget_tokens`.

**Adaptive thinking і бюджет токенів (виявлено 2026-09).** У Sonnet 5 міркування моделі увімкнені за замовчуванням і **ділять `max_tokens` з текстом відповіді**. Старий ліміт 2048 міг повністю з'їстися міркуваннями (відтворено: 1427 з 2048 токенів пішли на thinking) → обрізана або порожня відповідь. Тепер:
- `MAX_ANSWER_TOKENS=8000`, `MAX_DOCUMENT_TOKENS=12000`;
- глибина міркувань явно через `output_config.effort` (`CLAUDE_EFFORT`, за замовчуванням `medium`; заміри: low ≈ 20 с, medium ≈ 22–27 с на питання чату);
- `llm/claude.py` обробляє `stop_reason`: `refusal` → 422, `max_tokens` → помилка для JSON / примітка «відповідь обрізана» для тексту; порожня відповідь → помилка, а не порожній екран;
- кожна помилка API мапиться на зрозуміле повідомлення (ключ, ліміти, баланс кредитів, таймаут, мережа), фронтенд показує його з кнопкою «Спробувати ще раз».

**Швидка повторна спроба (2026-09).** Зрідка модель «задумується» надовго: зафіксовано 7820 з 8000 токенів і 115 с на одне питання — ще трохи, і лікар отримав би помилку. Тепер `ask_claude` при вичерпанні ліміту токенів, таймауті, порожній чи зламаній відповіді робить ОДНУ повторну спробу без міркувань (`thinking: disabled`, effort low, ≤ 50 с) і пише причину в `usage.fallback` аудит-логу. Бюджет часу: перша спроба ≤ `CLAUDE_TIMEOUT_SECONDS=80`, швидка ≤ 50 с — разом менше за таймаут фронтенду (150 с). Короткі збої API (529 overloaded, 5xx, обрив з'єднання) повторюються один раз усередині `_create`; автоматичні повтори SDK вимкнені — вони повторювали й таймаути (3 × таймаут > терпіння лікаря). Відмова моделі (refusal), 429, невірний ключ і нестача кредитів не повторюються. Покрито тестом з підмінними відповідями API (усі гілки).

### Стабільність сервера (інцидент на демо 2026-09)
Симптом: після кількох запитів сайт на Railway переставав відповідати на все (чат і документи) — таймаути, потім 502. Найімовірніша причина — нестача пам'яті контейнера (torch + embedding-модель + ChromaDB) після завершення trial-ліміту; попередня перевірка деплою робилась лише поверхневим `/api/health`, який цього не ловив. Зроблено:
- `torch` ставиться CPU-збіркою (без CUDA-бібліотек — суттєво менший образ і RSS);
- embedding-модель прогрівається при старті (`main.py`), а не на першому запиті лікаря; у лог пишеться RSS / ліміт пам'яті cgroup / кількість чанків;
- `/api/health?deep=true` тепер робить **реальний** embedding + реальний виклик Claude і повертає пам'ять процесу (`app/sysinfo.py`); `vector_store` вважається ok, лише якщо в базі > 0 чанків;
- усі залежності закріплені точними версіями (`requirements.txt`), щоб збірка на сервері не підтягнула несумісну мажорну версію.
Після деплою перевіряти **справжніми питаннями чату і генерацією документа**, а не лише health.

### Embeddings
`intfloat/multilingual-e5-base` через `sentence-transformers`. Модель E5 вимагає префіксів `query:`/`passage:` — інкапсульовано в `rag/embeddings.py`. Модель у конфізі (`EMBEDDING_MODEL`).

### Чанкінг
За токенами embedding-моделі (~500, перекриття ~80), з повагою до меж секцій markdown — щоб метадані `section` були коректні. Метадані чанка: `source_name`, `document_number`, `date`, `section`.

Ембединг рахується з тексту `"{title}. {section}\n{text}"` (назва статті з front-matter `title` + заголовок розділу), а в базі зберігається чистий текст чанка. Без цього чанк на кшталт «Показання до операції» не знав, до якого перелому він належить, і програвав у пошуку.

### Гібридний пошук: векторний + BM25 (2026-09)
На 819 чанках однодоменного тексту multilingual-e5-base дає десяткам фрагментів майже однакові відстані (0.13–0.15), і точні терміни питання губляться: напр. «розрив передньої хрестоподібної зв'язки» не піднімав розділ про «ПХЗ», «вогнепальний перелом стегна» — статтю про вогнепальну травму. Тому `rag/retriever.py` зливає два списки кандидатів (по 30) через Reciprocal Rank Fusion:
- векторний (E5) — ловить перефрази, синоніми, питання російською;
- лексичний BM25 (`rag/lexical.py`, без зовнішніх залежностей, індекс у пам'яті з чанків Chroma) — ловить точні терміни й епоніми. Морфологія — обрізання слова до 5-літерного префікса; медичні скорочення (ПХЗ, ВТЕУ, ТЕЛА, НМГ, АВН…) розгортаються в повні назви і в чанках, і в питаннях.

Заміри на 32 питаннях з відомою статтею-відповіддю: потрібна стаття в top-10 — векторний 29/32, BM25 31/32, **RRF 32/32**. Варіант «гарантовані топ-3 з кожного списку» перевірено — не кращий (31/32).

Точніше, на рівні **розділу**: незалежний аудит відповідей показав, що стаття знаходиться, але профільний розділ («лікування розриву ПХЗ і показання до реконструкції», «DAIR при FRI», «Gustilo-Anderson: тип II») часто не потрапляв у контекст. Тому: заголовок розділу в BM25 має вагу ×3, `RAG_TOP_K` 10 → 14. Заміри на 14 парах «питання → профільний розділ»: 4/14 → 8/14.

Чанки одного розділу зливаються в один фрагмент (`retriever.group_by_section`) перед промптом, а посилання у відповіді перенумеровуються підряд у порядку появи (`api/chat.py`, `_renumber_citations`) — раніше [1] і [5] могли вести на той самий розділ, а нумерація мала пропуски.

Поріг `RAG_MAX_DISTANCE` застосовується до векторного списку: якщо жоден чанк його не пройшов — вважаємо питання явно нерелевантним (погода → порожньо), лексичні збіги такий запит не «рятують». Відомий залишковий промах: питання, сформульовані зовсім іншими словами, ніж стаття («нагноєння рани після остеосинтезу» vs стаття «fracture-related infection») — відповідь тоді йде з блоку загальних знань. Покращення — реранкер або переформулювання запиту LLM (TODO «Реранкер»).

### База знань (стан на 2026-09)
~38 довідкових оглядів (`data/sources/*.md`) з основних розділів травматології: переломи всіх основних локалізацій, вивихи, хребет, таз, політравма/DCO, вогнепальна та мінно-вибухова травма, відкриті переломи, компартмент-синдром, ВТЕУ, FRI, діти, літні, гіпсова іммобілізація тощо. **Усі написані AI** і позначені `[ЧЕРНЕТКА, не офіційне джерело]` у `source_name` (мітка видна в кожній цитаті). Кожна стаття проходить автоматичну перевірку двома незалежними AI-рецензентами (класифікації/анатомія/числа і тактика/безпека) з подальшим внесенням виправлень. Це **не замінює експертну перевірку** — мета бази: дати консультанту змістовні відповіді для оцінки і зібрати його правки; остаточно — заміна/звірка з реальними протоколами.

### Локальна підстановка даних пацієнта (без AI)
Проблема (запит фаундера 2026-07-06): плейсхолдери `[ВКАЗАТИ: ПІБ, дата народження, № картки...]` у чернетках документів доводилось заповнювати вручну після генерації — незручно, коли таких полів багато (виписний епікриз).

Рішення: для полів, що ідентифікують пацієнта, `DOC_TEMPLATES["discharge_summary"]` (`app/prompts.py`) інструктує модель вставляти стабільні токени `{{PATIENT_NAME}}`, `{{PATIENT_DOB}}`, `{{PATIENT_SEX}}`, `{{CARD_NUMBER}}`, `{{ADMISSION_DATE}}`, `{{DISCHARGE_DATE}}`, `{{DOCTOR_NAME}}` — дослівно, без змін. Ці токени LLM ніколи не бачить заповненими: справжні значення лікар вводить в окремі поля на фронтенді (`DocumentsView.jsx`, `PASSPORT_FIELDS`), які **ніколи не входять у payload `generateDocument()`** — тобто не йдуть на бекенд, до Claude API чи в audit-лог. Підстановка (`fillPassportTokens`) відбувається суто в браузері, вже після отримання тексту від бекенда. Незаповнене поле коректно деградує до звичного `[ВКАЗАТИ: ...]`. Перевірено 2026-07-06: реальні тестові ПІБ/номер картки відсутні в `logs/audit-*.jsonl` після генерації.

Уточнення 2026-09 (за аудитом згенерованих документів): модель інколи вигадувала власні токени кирилицею (`{{ПІБ}}`, `{{ДАТА_ПОЧАТКУ_ДОСЛІДЖЕННЯ}}`) в інших типах документів — промпт тепер дозволяє лише задані шаблоном токени, а фронтенд будь-який непередбачений `{{…}}` перетворює на `[ВКАЗАТИ: …]`. Рядок «Дата операції: {{OPERATION_DATE}}» додається до шаблону лише якщо лікар заповнив поле втручання (інакше модель вставляла його «про всяк випадок»).

Це стосується лише «Паспортної частини» виписного епікризу (єдиний шаблон, що має чітко визначені ідентифікуючі поля) — `case_history_section` і `dissertation_section` як і раніше покладаються на звичайні `[ВКАЗАТИ: ...]` для будь-яких відсутніх даних.

### Безпека і етика (закладено з першого дня)
- Дані, що ідентифікують пацієнта, **не логуються**. Аудит-лог містить лише текст запиту, джерела, відповідь, usage (`app/audit.py`).
- Коментарі-нагадування у місцях прийому вводу від лікаря (`api/chat.py`, `api/documents.py`).
- UI попереджає лікаря не вводити персональні дані.
- Генератор документів інструктований не вигадувати числові клінічні дані — замість них плейсхолдери `[ВКАЗАТИ: ...]`.
- Кожна відповідь чату містить дисклеймер про допоміжний характер.
- Усі виклики Anthropic API логуються для аудиту якості.

Виявлено наживо: флагманське питання з брифу («тактика при відкритому переломі гомілки з раною 4 см») перестало коректно відповідати після переіндексації, бо потрібний чанк («Тип II», відстань 0.2000, у межах порогу 0.22) був 6-м за рангом і `RAG_TOP_K=5` відкидав його ще до перевірки порогу. **Фікс:** `RAG_TOP_K` піднято до 10, щоб поріг `RAG_MAX_DISTANCE` був реальним фільтром, а не обрізаним заздалегідь списком.
