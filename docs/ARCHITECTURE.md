Документ фіксує прийняті рішення і те, що свідомо спрощено або відкладено, щоб при масштабуванні не сплутати MVP-компроміси з фінальною архітектурою.

## Ключові рішення

### RAG-grounded відповіді
Відповідь чату формується **лише** з фрагментів, знайдених у векторній БД. Якщо `retrieve()` повертає порожній список (немає чанків нижче порогу відстані) — Claude **не викликається взагалі**, користувач отримує «недостатньо даних у базі знань». Це головний запобіжник проти галюцинацій.

- Поріг релевантності: `RAG_MAX_DISTANCE` (косинусна відстань, 1 − cos_sim). Підбирається під embedding-модель.
- Системний промпт вимагає: посилання на джерело для кожного клінічного твердження, відмову при нестачі даних, відмову на питання поза травматологією, заборону вигадувати числові дані.

**Калібрований поріг і його межа (виміряно на прикладних джерелах, multilingual-e5-base):**

| Тип запиту | top-3 дистанції |
|---|---|
| Релевантний (типи переломів AO/OTA) | 0.093 / 0.115 / 0.135 |
| Релевантний перефраз (відкритий перелом гомілки) | 0.152 / 0.190 / 0.192 |
| Нерелевантний медичний (кардіологія) | 0.187 / 0.201 / 0.217 |
| Нерелевантний медичний (гастро) | 0.190 / 0.203 / 0.206 |
| Нерелевантний немедичний (погода) | 0.239 / 0.261 / 0.268 |

Висновок: релевантні перефрази (до 0.192) і медично-суміжні чужі теми (кардіологія від 0.187) **перекриваються** — самим лише порогом їх чисто не розділити (обмеження малої мультимовної моделі на однодоменному тексті). Тому захист дворівневий: (1) поріг `0.22` відсікає грубо чуже (погода → детермінований «недостатньо даних», без виклику LLM); (2) медично-суміжні поза травматологією відсіює LLM за правилом 4 системного промпта. Справжнє рішення для тонкої тематичної фільтрації — краща/більша embedding-модель або реранкер (див. TODO).

### Цитування
Порядок цитат детермінований: чанки нумеруються `[1..N]` у промпті, і `citations[N-1]` у відповіді API відповідає посиланню `[N]` у тексті. Список джерел будується з метаданих чанків, а не з тексту моделі.

### Дисклеймер
Додається до кожної відповіді **детерміновано** (окреме поле API), не покладаючись на модель.

### Абстракція VectorStore
`app/rag/vector_store.py` визначає інтерфейс `VectorStore` (add/query/count/reset). Реалізація — `ChromaVectorStore`. Перехід на pgvector/Pinecone = нова реалізація інтерфейсу без змін у retriever/ingestion.

### Модель Claude у конфігу
Назва моделі винесена в `CLAUDE_MODEL` (`.env`). `claude-sonnet-5` не приймає `temperature`/`top_p`/`budget_tokens` — обгортка `llm/claude.py` передає лише `model`/`max_tokens`/`system`/`messages`, тож зміна моделі не потребує правок коду.

### Embeddings
`intfloat/multilingual-e5-base` через `sentence-transformers`. Модель E5 вимагає префіксів `query:`/`passage:` — інкапсульовано в `rag/embeddings.py`. Модель у конфізі (`EMBEDDING_MODEL`).

### Чанкінг
За токенами embedding-моделі (~500, перекриття ~80), з повагою до меж секцій markdown — щоб метадані `section` були коректні. Метадані чанка: `source_name`, `document_number`, `date`, `section`.

### Безпека і етика (закладено з першого дня)
- Дані, що ідентифікують пацієнта, **не логуються**. Аудит-лог містить лише текст запиту, джерела, відповідь, usage (`app/audit.py`).
- Коментарі-нагадування у місцях прийому вводу від лікаря (`api/chat.py`, `api/documents.py`).
- UI попереджає лікаря не вводити персональні дані.
- Генератор документів інструктований не вигадувати числові клінічні дані — замість них плейсхолдери `[ВКАЗАТИ: ...]`.
- Кожна відповідь чату містить дисклеймер про допоміжний характер.
- Усі виклики Anthropic API логуються для аудиту якості.
