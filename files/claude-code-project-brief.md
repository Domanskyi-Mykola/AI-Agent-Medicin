# Завдання для Claude Code: MVP-каркас AI-асистента травматолога

Скопіюй усе нижче і встав як перше повідомлення в Claude Code у порожній папці проєкту.
Якщо встигаєш до закінчення безкоштовного вікна Fable 5 — онови модель на неї саме для цієї, найважчої архітектурної сесії; далі веди розробку на Sonnet 5.

---

## Контекст проєкту

Я розробляю MVP AI-асистента для лікарів-травматологів та інтернів в Україні. Продукт вузько сфокусований на травматології/ортопедії (не універсальна медицина). Дві ключові функції:

1. **Клінічний Q&A** — лікар/інтерн ставить питання (наприклад, "яка тактика при відкритому переломі гомілки з раною 4 см"), система відповідає на основі перевіреної бази знань (протоколи МОЗ України, класифікаційні системи AO/OTA, Gustilo-Anderson тощо) і **обов'язково** вказує джерело/протокол, на який спирається.
2. **Асистент документації** — генерація чернеток виписних епікризів, розділів історії хвороби та розділів дисертацій за структурованим вводом лікаря (діагноз, втручання, перебіг).

Це рання стадія: я соло-фаундер з обмеженим бюджетом. Мета зараз — робочий локальний прототип, який можна показати практикуючому травматологу (моєму медичному консультанту) для валідації, а не production-система.

## Що потрібно зробити зараз

Створи повний каркас проєкту (scaffold) і один наскрізний робочий приклад (end-to-end), який я зможу запустити локально.

### 1. Структура репозиторію

Створи монорепо:
```
/backend       — FastAPI (Python)
/frontend      — React + Vite + Tailwind
/ingestion     — скрипти завантаження/чанкінгу/ембедингу джерел у векторну БД
/docs          — README, ARCHITECTURE.md
```

### 2. Технологічний стек (використовуй саме це, не пропонуй альтернатив без причини)

- **Backend:** Python + FastAPI
- **LLM:** Anthropic Claude API (Python SDK `anthropic`). Модель за замовчуванням — `claude-sonnet-5` для чату/документів; винеси назву моделі в конфіг, щоб легко міняти.
- **Векторна БД:** ChromaDB, локально, без зовнішніх залежностей (просто для MVP; сумісність з переходом на pgvector/Pinecone пізніше має бути закладена через простий інтерфейс `VectorStore`, а не хардкод).
- **Embeddings:** будь-яка модель з бібліотеки `sentence-transformers`, яка непогано працює з українською (наприклад `intfloat/multilingual-e5-base`) — постав це як змінну конфігурації.
- **Frontend:** React + Vite + Tailwind, мінімальний UI (3 екрани: чат, документи, калькулятори — дизайн я вже маю окремо, зараз важлива лише функціональна частина).
- **Auth:** заглушка (mock user), повноцінну автентифікацію додамо пізніше.
- **Конфігурація:** `.env` для `ANTHROPIC_API_KEY` та інших секретів, `.env.example` в репозиторії з порожніми значеннями.

### 3. Backend — обов'язкові модулі

**`/backend/ingestion`**
- Скрипт, який приймає текстові/markdown файли з `/data/sources/` (протоколи, класифікації), розбиває на чанки (~500 токенів, з перекриттям), рахує ембединги, зберігає в ChromaDB з метаданими: `{source_name, document_number, date, section}`.

**`/backend/rag`**
- Функція `retrieve(query: str, top_k: int) -> list[Chunk]` — пошук релевантних чанків.
- **Критично важливо:** відповідь LLM повинна формуватися ЛИШЕ на основі знайдених чанків (RAG-grounded), а не вільної генерації з пам'яті моделі. Якщо релевантних чанків не знайдено — модель повинна прямо сказати "недостатньо даних у базі знань" замість вигадування відповіді.

**`/backend/api/chat.py`**
- POST `/api/chat` — приймає питання, робить retrieve(), формує промпт із знайденими чанками + інструкцією цитувати джерело, викликає Claude API, повертає `{answer, citations: [{source, document_number}]}`.
- Системний промпт має явно вимагати: (а) відповідати тільки на основі наданого контексту, (б) завжди вказувати джерело для кожного клінічного твердження, (в) додавати дисклеймер, що відповідь не замінює рішення лікаря, (г) якщо питання виходить за межі травматології/ортопедії — чесно повідомляти про обмеження системи, а не намагатися відповісти.

**`/backend/api/documents.py`**
- POST `/api/documents/generate` — приймає `{doc_type, diagnosis, procedure, notes}`, формує промпт-шаблон під конкретний тип документа (епікриз / розділ історії хвороби / розділ дисертації), викликає Claude API, повертає згенерований текст.
- **Важливо:** промпт має явно інструктувати модель НЕ вигадувати конкретні числові клінічні дані (дати, дозування, результати аналізів), яких лікар не вказав — тільки структурувати та формулювати те, що передано у вводі.

**`/backend/api/health.py`**
- GET `/api/health` — перевірка, що бекенд, векторна БД і Anthropic API доступні.

- Прожени їх через ingestion-скрипт, щоб я одразу побачив, що RAG працює.

### 5. Frontend — мінімум для перевірки пайплайну

Не потрібно повторювати весь дизайн зараз — досить одного простого екрану з полем вводу питання, кнопкою "Надіслати" і виводом відповіді + списку джерел під нею. Головне — щоб `/api/chat` реально відпрацював end-to-end через UI.

### 6. Безпека і етика (закласти з першого дня, не відкладати)

- Ніде не логувати і не зберігати дані, що ідентифікують пацієнта (додай коментар-нагадування в коді там, де приймається ввід від лікаря).
- Кожна відповідь чату повинна містити дисклеймер про допоміжний характер інструменту.
- Всі виклики до Anthropic API повинні логуватися (питання, знайдені джерела, відповідь) в локальний файл/таблицю для подальшого аудиту якості — без персональних даних пацієнтів.

### 7. Що маю отримати в результаті цієї сесії

1. Робочий репозиторій з описаною структурою.
2. `README.md` з інструкцією: як встановити залежності, підняти ChromaDB, запустити ingestion, запустити backend і frontend локально.
3. Один реально працюючий наскрізний приклад: я запускаю ingestion на прикладних файлах → задаю питання через UI → отримую відповідь із коректним посиланням на джерело.
4. `docs/ARCHITECTURE.md` з коротким описом прийнятих рішень і того, що свідомо залишено "на потім" (auth, платежі, продакшн-БД тощо), щоб я не забув, що це MVP-спрощення, а не фінальна архітектура.
